# TG 工具箱：Windows 与 Work 网页统一数据架构

## 目标

Windows 与私人 Work/Sites 网站提供尽量一致的五工具体验，并让重要业务数据在本地 SQLite、云端业务库和同步网关之间安全流动。两端不是共享同一个数据库文件，而是共享同一套实体键、状态语义和同步日志。

```text
Telegram / 导入文件
        │
        ├── Windows：长期 MTProto / Bot 执行器 ── 本地 SQLite
        │                                      │
        └── Work：按请求 MTProto / Bot 执行器 ── 云端 D1
                                               │
                         双向增量 Push / Pull ─┤
                                               ▼
                                     独立同步网关 D1
```

## 产品边界

- Telegram 个人 API 和 Bot 均只在“Telegram 连接中心”配置一次；五个工具只绑定已经发现的来源。
- Windows 和网页都保留各自的 Telegram Session。Session、Token、`api_hash`、验证码、密码、Cookie 永不进入同步载荷。
- 每个 Telegram 来源同一时刻只能有一个执行端推进远端 checkpoint、Bot offset 或已读位置。执行前取得 `telegram:<连接>:<来源>` 租约，失去租约立即停止远端副作用。
- 本地断网时继续使用并写入 outbox；恢复联网后分批上传。网页不可用不影响 Windows 本地历史与过滤。
- 删除同步为墓碑。普通更新不能静默复活已删除实体；恢复必须是用户明确操作。
- 历史回拉不自动标已读。`never`、`manual`、`safe_auto` 三种策略在两端含义相同，已读 ID 和 checkpoint 只允许前进。

## 同步范围

### 必须双向同步

- 五工具永久记录及关键标签、状态、来源链接。
- 处理批次、结果明细和任务摘要；原始输入最多同步 64 KiB 预览，完整原文继续保存在创建端。
- Telegram 来源、工具绑定、统一消息池、工具独立队列。
- Telegram 增量 checkpoint、已读策略和安全已读位置。
- 任务中心条目。
- MissAV 参考女优 Tag、参考库黑名单、Raindrop 导出黑名单。
- 非敏感、跨端有意义的工具设置。

### 只留在执行端

- Telegram `api_id`、`api_hash`、手机号、验证码、2FA 密码和 Session。
- Bot Token、Raindrop Token、Cookie、浏览器存储和网站登录状态。
- 代理地址、本地文件路径、数据库路径、下载缓存和运行临时文件。
- 大体积日志、浏览器脚本正文和可重新生成的导出文件。

## 三个数据层

1. **业务库**：Windows SQLite 和 Sites D1 各自为本端 UI 提供快速分页、搜索、编辑和历史。
2. **同步网关**：保存规范化实体、递增变更序列、墓碑、冲突和执行租约，不直接承担工具页面查询。
3. **本端同步状态**：保存 node ID、最后拉取序列、outbox、实体版本、冲突和最近同步统计。Windows 设备令牌使用 DPAPI 文件保存；网页仅从 Site Secret 读取服务凭据。

## 同步循环

1. 本端业务事务成功后，在同一事务中写入 outbox。
2. Push 按最多 200 条、请求体安全目标 3.5 MB（网关硬上限 4 MB）分批上传；`operationId` 保证重试幂等。单次 Web 请求只执行有界批数，若仍有数据必须显式返回 `incomplete`、`remaining` 与 `hasMore`，浏览器重新生成预览后续跑；不得用分页硬上限静默截断或提前更新最近成功时间。
3. 网关按实体自然键合并，生成递增 `sequence`，返回接受、重复或冲突。
4. Pull 从本端游标之后读取，逐批写入业务库和本端实体版本；业务写入与游标推进必须同一事务。Pull 同样采用有界请求和显式续跑，浏览器关闭或后续页失败后仍能从已提交游标继续。逐页提交不得更新 `last_success_at`；只有整个同步完整结束才能更新最近成功时间。
5. 对冲突给出可见记录。checkpoint/已读位置取最大值，队列状态禁止无意倒退，删除墓碑优先，其他字段按时间和 node ID 稳定裁决。
6. 首次配对可选择：仅上传本地、仅下载云端或先生成双向对比预览。不得默认覆盖正式数据。

## Telegram 执行协调

- 租约键与 Windows 完全一致：Bot 全局游标固定为 `telegram:bot:global-offset`；个人账号来源为 `telegram:personal:<external-chat-id>`。
- Telegram 同步实体的跨端来源自然键固定为 `telegram_personal:default:<external-chat-id>` 或 `telegram_bot:default:<external-chat-id>`。网页本地连接 ID `telegram-personal` / `telegram-bot` 只是存储别名，不得进入跨端身份；具名的其他连接 ID 继续保留。
- 租约在消息分块写入后、checkpoint/offset 最终提交前仍须再次验证；续租刷新到期时间，剩余时间不足安全窗口时不得推进远端位置。此时失约可以保留已写入的幂等消息，但必须阻止最终 offset/checkpoint 批次并把运行标记为失败。
- 租期 120 秒，每 30 秒续约；网关不允许超过 120 秒，异常退出后自动过期。
- 本地长期连接可以持续工作，但仍必须持有租约。
- 网页按请求连接，每次请求先取得租约，完成或失败后释放。
- 租约只防止同时执行远端副作用；本地过滤、表格编辑和导出不需要租约。

## UI 对齐

两端都使用以下一级入口：

- 工具首页
- 处理中心
- 数据中心
- Telegram 连接中心
- 同步中心
- 日志
- 设置与备份

每个工具保持相同工作流：输入 / Telegram 消息 / 结果 / 专用操作 / 历史。结果页必须提供可全选、可多选的表格，以及一行一个的纯文本结果框和“复制所选/复制当前范围/TXT/CSV”。

同步中心必须显示：当前节点、连接状态、待上传、待下载、冲突、最近成功时间、当前执行租约，以及“预览”“Push”“Pull”“双向同步”四个明确动作。自动同步只能作为用户可关闭的选项。

## 首次上线顺序

1. 先部署空同步网关并运行 D1 迁移，不接正式数据。
2. 网页接入网关，生成云端管理员设备身份；只做快照预览。
3. Windows 用一次性配对码配对；设备 Token 只写入 DPAPI 文件。
4. 对本地和云端各做完整备份，生成差异报告。
5. 用户选择首次方向后执行，并核对数量、抽样内容和冲突。
6. 开启日常手动双向同步；稳定后再考虑启动时/定时自动同步。

## 完成标准

- 两端同一永久记录不会重复；同一 Telegram 消息按账号、来源、消息 ID 唯一。
- 两端分别编辑后能产生可解释结果或可见冲突，不静默丢数据。
- 编辑、删除、队列状态、checkpoint 和已读位置能往返同步。
- 同一来源不能被本地和网页同时远端拉取或标已读。
- 断网、重复提交、进程中断和分页续传不造成漏项或重复副作用。
- 仓库、日志、D1 同步载荷均不出现 Secret 或 Telegram Session；同步协议同时检查敏感字段名和字符串正文中的 Token、Bearer、登录链接、Session 等特征。
- 五个工具的入口、处理阶段、表格操作和文本输出在两端保持同一语义。
