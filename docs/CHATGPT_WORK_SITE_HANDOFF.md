### 5.3 Windows 独立回退能力

- Windows 端继续使用 DPAPI 加密自己的 Telegram 凭据与 Session；网站不得读取、迁移或复用该 Session。
- Windows 端继续提供个人账号 MTProto 登录、二维码/手机号/验证码/两步验证、来源发现、历史、增量和已读能力，作为网站故障时的独立回退。
- 复用本地 Chrome 登录状态。
- Chrome 扩展桥、配对码和本地串行收藏。
- 123AV APP 内账号窗口和账号收藏。
- 本机任意目录直接读写。

Windows 回退不缩减网站 Telegram 范围。只有 123AV 账号操作、本机浏览器与任意目录读写仍是明确的 Windows-only 能力。

### 5.4 Telegram 双 API 网站策略

- 可以实现用户手动触发的 Bot API 增量接收，但 Token 只能放在 Site Secret。
- 不做永久后台轮询，不承诺补回 Bot 加入前的历史。
- 一个 Bot 的 `getUpdates` 是全局队列；消息必须一次安全分发到所有已绑定工具，不能为每个工具伪造独立远端游标。
- 网站个人账号 API 必须尽可能复刻 Windows v0.5.13：
  - `api_id`、`api_hash` 的所有者私密配置。
  - 二维码登录，以及国际格式手机号、验证码和两步验证密码登录。
  - 明确的登录阶段、超时、取消、解锁、恢复已保存登录、注销并删除网站 Session。
  - 发现普通群、超级群和广播频道；最多保存 100 个来源。
  - 每个工具分别绑定多个来源；同一来源可绑定多个工具。
  - 最近消息、指定时间、历史回拉和日常增量；数据库端分页与连续检查点。
  - 来源 ID + 消息 ID 去重、正文共享、工具独立队列。
  - `safe_auto`、`never`、`manual` 三种已读策略；历史回拉永不自动标已读；手动确认后按 `max_id` 标记已读。
- 网站端 Session 必须服务端加密后保存。手机号、验证码、两步验证密码和二维码内容只存在于仅所有者可访问的登录流程短时内存，不得落入 D1、浏览器持久存储、日志或错误堆栈。
- 网站与 Windows 端不得共享或覆盖 Telegram Session、检查点或已读状态。
- 若 Sites 运行时实测不稳定，网站通过仅所有者可访问、双向鉴权的私有 MTProto 后端实现上述能力；Site 仍是唯一用户界面和业务数据库边界。

## 6. 五个工具的关键业务规则

### 6.1 推特博主

- 以每条 Telegram 消息里的 ASCII `#标签` 为主要来源。
- 保留可信 `@handle` 和 `x.com` / `twitter.com` 主页链接作为兜底。
- 排除过短主题标签、传送门标签和推广机器人。
- 用户名大小写不敏感去重，保持首次出现顺序。
- 输出两个独立区域：用户名一行一个、`https://x.com/用户名` 一行一个。

### 6.2 Bad.news

- 只接受 `https://bad.news/t/数字`。
- 去掉查询参数、片段和末尾无关路径。
- 排除 `/app`、官网入口、栏目页、广告和其他站点链接。
- 输出规范直达链接，一行一个。

### 6.3 海角帖子

- 只接受七类正文路径：`hjjd`、`hjmz`、`hjyc`、`hjfn`、`hjsz`、`hjrq`、`hjhj`。
- 路径必须是“栏目/数字.html”。
- 统一输出 `https://www.haijiaolove.xyz/栏目/数字.html`。
- 排除广告域名、旧域名、栏目首页、视频栏目和其他垃圾链接。

### 6.4 MissAV

- APP/网站只负责过滤番号和生成完整浏览器脚本，不直接从服务器查询 MissAV。
- 输入必须排除日期、时间、尺寸、文件大小、Office/电视型号、普通帖子 ID、用户名年龄和其他已知假番号。
- 可信 MissAV 详情链接中的番号应优先保留。
- FC2 规范化、去重和顺序必须与 v0.5.13 一致。
- 参考女优 Tag 库支持逐行编辑和从书签 HTML 完整替换。
- 默认基线来自用户给过的 `Miss_AV.html`：3,680 条书签、1,553 个女优 Tag。
- 完整浏览器脚本只注入当次番号、参考 Tag 和黑名单快照，不得擅自重写用户脚本核心流程。
- 脚本结果固定产生三个目录：`参考女优Tag命中`、`需要查找`、`其他`。
- `需要查找` 优先级最高。
- 第一层黑名单只取消参考命中资格，不删除参考库；影片仍可进入其他目录。
- 第二层黑名单命中后不得进入 Raindrop 导入 HTML/CSV，但必须留在报告和 JSON 备份中并写明原因。

### 6.5 123AV

- 网站第一版不承担真实查询和账号收藏。
- 网站保留番号任务、状态、结果导入、任务 CSV 导出和本地端操作说明。
- 不读取或索要 Cookie、密码、Local Storage、Session Storage 或完整页面 HTML。
- 不得把“生成任务”显示成“已收藏”。

## 7. 数据与状态语义

### 7.1 设计原则

- 五个工具的任务、结果、历史和 Telegram 队列状态相互独立。
- 永久记录与处理批次分开：批次是来源和审计，永久记录承担长期去重。
- 同一 Telegram 消息正文可共享保存一次，但在不同工具中的候选、已处理、忽略和运行状态必须独立。
- 所有批量写入必须使用事务。
- 删除业务数据前建立可恢复快照。
- 日志只读；业务数据才允许 CRUD。

### 7.2 网站建议实体

- `content_runs`：一次处理任务。
- `content_results`：任务结果。
- `permanent_records`：长期规范结果与去重索引。
- `reference_actress_tags`：参考女优 Tag。
- `reference_tag_blacklist`：第一层黑名单。
- `raindrop_export_blacklist`：第二层黑名单。
- `input_sources`：Telegram Bot、文件或其他来源。
- `tool_source_bindings`：来源与工具多对多绑定。
- `telegram_messages`：临时原文缓存和消息标识。
- `telegram_tool_queue`：每个工具独立的消息状态。
- `telegram_message_fingerprints`：来源 ID + 消息 ID 去重。
- `sync_transactions`：同步审计。
- `telegram_accounts`：网站个人账号连接状态；不得保存明文凭据或 Session。
- `telegram_auth_flows`：登录阶段、过期时间、取消状态和一次性挑战标识；不得保存手机号、验证码、密码或二维码内容。
- `telegram_source_checkpoints`：每个个人来源的连续增量、历史基线、安全可标位置和最近远端已读位置。
- `task_inbox`：统一处理中心。
- `script_generations`：脚本版本、哈希、任务和番号数，不重复保存大脚本。
- `app_logs`：脱敏日志。
- `data_snapshots`：高影响操作前的恢复点。

可以调整表名，但不得丢失这些语义和唯一性约束。

### 7.3 性能要求

- 按至少 100,000 条结构化数据设计。
- 数据库端分页、搜索、筛选和排序。
- 不得把全库一次加载到浏览器。
- 跨页全选应保存筛选条件或服务端选择集合，不能只选择当前 DOM 行。
- CSV/JSON 大批量导入使用分块解析、事务和可见进度。

## 8. 表格与交互验收

所有业务数据表应尽可能保持一致的表格操作：

- 单击选中整行。
- Ctrl 增减选中。
- Shift 连续选择。
- Ctrl+Shift 追加区间。
- 当前页全选和全部筛选结果全选必须分开。
- `Ctrl+A`、`Ctrl+C`、方向键、Enter 编辑、Delete 删除确认。
- 搜索、筛选、排序、分页、列宽、列顺序和隐藏列。
- 单元格编辑和长文本编辑器。
- 新增、修改、删除、查找替换和批量修改。
- 复制 TSV、粘贴表格区域、CSV 导入和 CSV/TXT/JSON 导出。
- 表格区域有足够高度、纵横滚动条和移动端可用布局。
- 高影响操作显示范围、数量和不可逆影响，并提供恢复点。

## 9. 输入、历史和 Telegram 工作页

- Telegram 消息工作页属于每个工具的“输入”模式，不是单独的全局一级页面。
- 每个工具可绑定多个群组/频道；同一来源可绑定多个工具。
- 绑定编辑器必须突出当前正在配置的工具，显示新增、移除和已绑定其他工具，避免错绑。
- 消息表格支持关键词、状态、候选、起止时间、分页和跨页选择。
- 用户只处理所选消息；空结果记录为 `processed_empty`，不能与未处理混淆。
- 可复制或导出所选原文。
- 处理成功后按用户决定删除正文，只保留结果、消息 ID、时间和必要审计字段。
- 网站个人 API 实现三种来源级已读策略。历史回拉永不自动标已读；`safe_auto` 只能在连续范围完整落库后执行；`manual` 必须由所有者确认并按本地记录的安全 `max_id` 提交；`never` 永不提交远端已读。

## 10. Raindrop 文件导出

网站恢复文件导出，不恢复 API Pull、Push 或双向同步。

- 支持 Raindrop 兼容书签 HTML 和官方列格式 CSV。
- 导出前执行第二层黑名单硬排除。
- 被排除记录仍进入报告/JSON 审计，不静默丢失。
- 导出预览和实际导出必须共用同一规则函数。
- 缺少有效链接的记录显示为排除或待复查。
- 不要求用户提供 Raindrop Token。

## 11. 安全与隐私

- Site 必须限制为 B 账号本人。
- 未登录或非所有者请求不能读取任何业务数据。
- Secret 只通过 Sites 设置注入服务器端。
- `TELEGRAM_API_ID`、`TELEGRAM_API_HASH`、`TELEGRAM_BOT_TOKEN` 只能通过 Site Secrets 或网站所有者私密配置提供。不得写入 Git、前端代码、构建产物、数据库或日志。
- 网站加密 Session 的密钥必须使用独立 Site Secret。若启用私有 MTProto 后端，其 URL 与站点到后端的鉴权密钥也必须使用 Site Secrets。
- 手机号、验证码、两步验证密码和二维码内容只允许在仅所有者可访问的登录界面短时使用；请求完成、取消或超时后立即从内存清除。
- 前端代码、构建产物、日志、错误堆栈和数据库不得泄露 Secret。
- 上传文件默认只用于本次解析；除非用户明确保存，不长期保留原文件。
- Telegram 正文按“处理成功后删除”策略执行。
- 对用户提供的 HTML、CSV、JSON 和文本做大小限制、类型检查和内容转义。
- 防止 CSV 公式注入、持久化 XSS、路径穿越、任意 SQL 和越权访问。
- 数据迁移先预览数量、冲突、坏行和将要覆盖的范围，再由用户明确确认。

## 12. 本地数据迁移边界

第一版先完成网站和导入器，不直接读取用户正式 SQLite。

后续迁移流程：

1. Windows 端只读打开正式数据库。
2. 做完整性检查和备份。
3. 导出不含密钥、会话、Token、Cookie 和本地绝对路径的迁移包。
4. 网站显示表级数量、重复、冲突、坏行和覆盖策略。
5. 用户确认后事务导入。
6. 导入后核对总数、抽样记录和唯一键。
7. 失败时回滚到导入前快照。

不要让用户把正式 SQLite、`-wal`、`-shm`、DPAPI 会话或浏览器配置直接上传到 Site。

## 13. 实现要求

- 使用 Sites 支持的项目结构，在 `apps/web-site/` 内工作。
- 这是多路由、持久化、认证和上传项目，应采用完整能力路径，不使用一次性静态页面方案。
- 使用 Sites 管理的持久化数据库和身份边界。
- 复用规则源码或移植为共享纯函数，并保留对应测试夹具。
- 不要通过复制 `generated/legacyBundle.js` 作为最终网站架构；应把权威规则整理为可测试模块。
- 不要依赖 Windows 路径、Tauri API、Node 原生 SQLite、DPAPI 或本机 Chrome。
- 在决定 MTProto 运行位置前，必须在当前部署运行不含真实凭据的网络与生命周期探针，并记录：原始 TCP、Telegram WebSocket、连接可持续时间、请求结束后的连接状态、Worker 重启/驱逐后的恢复能力，以及 Session 加密往返。

- 页面刷新后正式数据、历史和设置不得丢失。
- 所有错误需要给出可操作说明，不能只显示 `Error` 或原始堆栈。
- 完成实现后运行构建、规则回归、数据库测试、权限测试和移动端/桌面验收。
- 不要只提交计划；应一直完成到私人预览可访问，再报告结果。
